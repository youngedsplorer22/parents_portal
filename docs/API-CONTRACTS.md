# API contracts

This describes the HTTP API that the four public registration portals, the staff portal and the mobile app share. It is written so that another system (for example a future Sales ERP) could read the data through documented, stable structures. No ERP integration exists or is planned in this project; nothing here is specific to a frontend.

The server is the one source of truth. The browser sends only what a person typed or chose. It never sends an id that grants access, a role, a template, a status or a school: the server works those out from the signed-in session and its own records.

## 1. Conventions

**Transport.** JSON over HTTPS. Requests with a body send `Content-Type: application/json`. Responses are `application/json`. Every response from `/api/admin` and every authenticated route carries `Cache-Control: no-store`.

**Identifiers.** Every record id is a lowercase UUID (`xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`, version 4) generated by the database. Ids never change and are never reused. Text addresses (`slug` values) are separate from ids: they are for building links, not for identifying records in integrations.

| Thing | Id | Notes |
|---|---|---|
| School | `schools.id` | A school and a branch together are one row. |
| Trip (a tour) | `trips.id` | Belongs to one school (`school_id`). A school can have many trips, at the same time and over the years. |
| Person (parent account) | `parent_registrations.id` | One per email address. Holds the person's role. |
| Enrolment | `trip_enrolments.id` | One person on one trip. Unique per (person, trip). This is the stable key for "who registered for what". |
| Registration form | `onboarding_forms.id` | Belongs to an enrolment (`enrolment_id`). Once submitted it can no longer be changed. |
| Staff account | `staff_users.id` | |
| Itinerary item | `trip_itinerary_items.id` | |

**Relationships (stable).** `school 1—n trip`, `trip 1—n enrolment`, `person 1—n enrolment`, `enrolment 1—1 form (per trip)`. Nothing is deleted when a trip closes or when a registration template moves to another school; historical rows stay.

**Dates and times.** All timestamps are ISO 8601 in UTC with milliseconds and a `Z` suffix, for example `2027-01-31T08:30:00.000Z`. Dates without a time of day (a date of birth, a passport date) are `YYYY-MM-DD`. The academic year is the text `YYYY-YY`, for example `2027-28`.

**Names.** JSON properties are `camelCase`. Enumerated values are lowercase words or snake case, listed below. Unknown properties in a request are refused with a validation error (requests are strict), never silently ignored.

**Enumerations.**

| Name | Values |
|---|---|
| `tourType` | `domestic`, `international` |
| `paymentMode` | `none`, `payment` (the registration template: payment is, or is not, part of that registration workflow. It does not say whether the trip costs money.) |
| `templateKey` | `domestic_none`, `domestic_payment`, `international_none`, `international_payment` (= `tourType` + `_` + `paymentMode`, decided by the server) |
| trip `status` | `draft`, `active`, `closed`, `archived` |
| school `status` | `active`, `archived` |
| staff `role` | `sales` (the only role that can sign in; older `admin` rows are removed with `npm run ops -- admin:remove`) |
| parent `role` | `Student`, `Teacher`, `Team Leader` |
| form `status` | `draft`, `submitted` |
| staff account `status` | `pending` (no password yet), `active`, `inactive` |

**Display names for templates** (user-facing only; the `templateKey` values above do not change): Domestic — With Payment, Domestic — Without Payment, International — With Payment, International — Without Payment. "Without Payment" means payment is not part of that registration workflow.

**Errors.** Every failure has the same shape and an HTTP status that matches:

```json
{ "error": { "code": "VALIDATION_ERROR", "message": "Invalid request.", "fields": [ { "path": "title", "message": "Title is required." } ] } }
```

`code` is a stable machine value; `message` is for people. Extra detail properties may be present (`fields`, `retryAfterSeconds`, `attemptsRemaining`). Common codes:

| Status | `code` | Meaning |
|---|---|---|
| 400 | `VALIDATION_ERROR` | Malformed or invalid input. `fields` lists each problem. |
| 400 | `TRIP_REQUIRED` | A sign-up must come from a trip's registration link (when `PORTAL_BINDING_REQUIRED` is on). |
| 400 | `INVALID_ASSIGNEE` | Only active Sales accounts can be assigned to a trip. |
| 400 | `TEMPLATE_MISMATCH` | The trip is not of the registration template named. |
| 401 | `UNAUTHENTICATED` | No valid session. |
| 401 | `INVALID_CREDENTIALS` | Wrong email or password (one answer for unknown email, disabled account and wrong password). |
| 403 | `FORBIDDEN` | Signed in, but this role may not do this. |
| 403 | `CROSS_SITE_REQUEST` | A write from another site was blocked. |
| 404 | `NOT_FOUND` | No such record, or not yours to see. |
| 404 | `TRIP_NOT_FOUND` | A public registration address that names no public trip. One answer for unknown, misspelt, draft, archived, or page switched off. |
| 409 | `TRIP_NOT_OPEN` | The trip's page is public but it is not accepting registrations now (closed, outside its dates, or not the trip deployed on its template). |
| 409 | `INVALID_STATUS_CHANGE`, `TRIP_LOCKED`, `TRIP_ARCHIVED`, `SCHOOL_EXISTS`, `SCHOOL_ARCHIVED`, `STAFF_EXISTS`, `VERSION_CONFLICT`, `ALREADY_SUBMITTED` | State conflicts. |
| 429 | `RATE_LIMITED`, `SERVER_BUSY` | Slow down and retry (`retryAfterSeconds`). |

## 2. Authentication

There are three separate identities. A session of one kind never works for another.

| Identity | Sign in | Credential | Used for |
|---|---|---|---|
| Parent (Student, Teacher, Team Leader) | Email code (OTP) to register, then email and password | HttpOnly cookies `pp_access` (short) and `pp_refresh` | `/api/auth`, `/api/onboarding`, `/api/enrolments`, `/api/live-location` |
| Staff (Sales only) | Email and password. An account exists only if a developer added the exact email address (`npm run ops -- sales:allow`); the owner sets the password by emailed code. There is no admin account or login. | HttpOnly cookies `pp_staff_access` and `pp_staff_refresh` | `/api/admin` |
| Mobile app | Email and password | Bearer token pair in the response body (`Authorization: Bearer <token>`), no cookies | `/api/mobile` |

Cookies are `HttpOnly`, `SameSite=Strict`, `Secure` in production, and scoped to their own paths. A state-changing request that carries an `Origin` header must come from the same host. An access token that has expired answers `401 UNAUTHENTICATED`; the client then calls the matching `/refresh` route once and repeats the request.

There are no API keys. An integration would need its own identity added as a deliberate, reviewed change.

## 3. Public routes (no sign-in)

### `GET /api/join/{school}/{branch}/{trip}`
The public page of one trip. The three path values are the trip's address words (`schools.slug`, `schools.branch_slug`, `trips.slug`; a school with no branch uses `main`). They are not secret.

```json
{ "school": { "name": "ABC School", "branch": "Jaipur", "logo": "/api/school-logos/abc-school/jaipur?v=3" },
  "trip": { "title": "Jaipur 2027", "destination": "Jaipur", "tourType": "domestic" },
  "registrationOpen": true }
```
`branch` and `logo` are present only when set. The response holds no id, status, payment mode, template, dates or personal data. `registrationOpen` is `true` only when the trip is `active`, inside its dates, and is the trip deployed on its template (see "Portal deployments"). Unknown or non-public trip: `404 TRIP_NOT_FOUND`.

### `GET /api/school-logos/{school}/{branch}`
The school's logo image (`image/png`, `image/jpeg` or `image/webp`). `404` if none.

### Which public portal is calling
Each public portal's own web server adds a secret header `x-portal-key` to the `/api` calls it forwards, and removes any such header a browser sent. The API compares it with the configured `PORTAL_PROXY_SECRET_<TEMPLATE>` values and so knows which of the four portals a registration or enrolment came from. It is never read from the request body or any other header. With `PORTAL_BINDING_REQUIRED=true`, `POST /api/registrations` and `POST /api/enrolments` are accepted only from a recognised portal, only for the trip bound to that portal's template (otherwise `409 TRIP_NOT_OPEN`), and a sign-up with no trip is `400 TRIP_REQUIRED`.

### Email verification and registration
- `POST /api/email-otp/send`, `/resend`, `/verify`: email a 6-digit code and exchange it for a one-use `verificationToken`.
- `POST /api/registrations`: creates the parent account. Body: `firstName`, `lastName`, `role`, `phone`, `email`, `password`, `verificationToken`, and (from a trip's page) `publicTrip: { school, branch, trip }`. The server resolves the trip, checks that it is open and is the one deployed on its template, and creates the person and their enrolment together. `201` with the new account. `409 TRIP_NOT_OPEN` for a trip that is not accepting registrations.

## 4. Parent routes (parent session)

| Route | Purpose |
|---|---|
| `POST /api/auth/login`, `/login/password`, `/refresh`, `/logout`; `GET /api/auth/session` | Sign in and out. |
| `POST /api/auth/password-reset/request`, `/resend`, `/verify`, `/confirm` | Forgot password. |
| `GET /api/enrolments` | The caller's own enrolments (`{ enrolments: [...], legacy }`). |
| `GET /api/enrolments/resume` | Which registration to open after login. |
| `POST /api/enrolments` body `{ trip: { school, branch, trip } }` | Enrol the caller on another trip (same checks as registration). |
| `GET /api/enrolments/{enrolmentId}/itinerary` | The itinerary of the trip of one of the caller's OWN registrations: `{ trip: { title, destination }, items: [ { id, dayNumber, position, title, details, updatedAt } ] }`. Read-only, and still available after the trip is closed. Another person's id, an unknown or malformed id: `404 NOT_FOUND` with no data. |
| `GET /api/onboarding` | The forms for the caller's role and the caller's saved form. |
| `PUT /api/onboarding` | Save a draft: `{ tourType, data, currentSection, version, enrolmentId? }`. Partial answers are accepted (save and resume). |
| `POST /api/onboarding/submit` | Submit. The server validates the whole saved form again; every required field must be present and valid. |
| `GET /api/onboarding/pdf/status`, `POST /api/onboarding/pdf/retry`, `GET /api/onboarding/pdf` | The registration PDF (generated and copied to the company Google Drive at submission) and its download. |

A form in the response:
```json
{ "tourType": "domestic", "role": "student", "status": "draft", "data": { "fullName": "Asha Rao" },
  "currentSection": "personal", "version": 4, "updatedAt": "2027-01-31T08:30:00.000Z", "submittedAt": null,
  "progress": { "percent": 13, "requiredTotal": 8, "requiredDone": 1, "sections": [ { "id": "personal", "requiredTotal": 4, "requiredDone": 1, "status": "incomplete" } ] } }
```
The caller can reach only their own enrolments and forms; any other id is `404`.

## 5. Staff routes (Sales session, `/api/admin`)

The Sales API is sign-in, password and itinerary, and nothing else. There is **no admin API**: no route exists for schools, trips, staff, assignments, portal bindings, logos, audit or live-location administration. Any other address under `/api/admin` answers a signed-in Sales user `404 NOT_FOUND` (and anyone without a session `401`). Those operations are developer commands (`docs/DEVELOPER-CLI.md`), not HTTP.

Authentication: `POST /auth/login`, `/auth/logout`, `/auth/refresh`, `GET /auth/session`, `POST /auth/password`, and the first-time setup / forgot-password flow `POST /auth/password/request`, `/resend`, `/verify`, `/confirm`. A code is sent only to an address on the Sales list.

### 5.1 Itinerary (Sales, for assigned trips only)
A Sales person reaches a trip only while a developer has assigned it to them. One person may hold many trips and one trip may have many people.

Item:
```json
{ "id": "…", "tripId": "…", "dayNumber": 1, "position": 0, "title": "Arrive in Jaipur", "details": "Check in.", "createdAt": "…", "updatedAt": "…" }
```
| Route | Body | Result |
|---|---|---|
| `GET /itinerary/trips` | | `{ trips: [ { id, title, destination, academicYear, tourType, status, schoolName, schoolBranch, itineraryCount } ] }`, only the assigned trips |
| `GET /trips/{tripId}/itinerary` | | `{ items: [Item] }` ordered by `dayNumber`, `position` |
| `POST /trips/{tripId}/itinerary` | `{ dayNumber 1–366, title 1–200 chars, details? ≤ 2000, position? 0–999 }` | `201 { item }` |
| `PATCH /trips/{tripId}/itinerary/{itemId}` | any of the same fields (at least one) | `{ item }` |

A trip that is not assigned to the caller, or that does not exist, answers `403 FORBIDDEN` (the same answer, so it reveals nothing). The item must belong to the trip in the URL. There is no delete route.

## 6. Mobile routes (`/api/mobile`, bearer token)
`POST /auth/login`, `/auth/refresh`, `/auth/logout`; `GET /me`; `GET /trips`, `GET /trips/{enrolmentId}`; `POST /trips/{enrolmentId}/start`, `/location`, `/stop`. These use the same live-location rules as the website.

## 7. Operational routes
`GET /api/health/live` (the process answers) and `GET /api/health/ready` (the database answers). No authentication.

## 8. Change policy
Adding a property to a response, or a new route, is compatible. Renaming or removing a property, changing an id format, a date format or an enumerated value, or changing which role may call a route, is a breaking change and needs the lead's approval and an update to this file.
